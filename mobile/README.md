# MyCampusView for Android

A native React Native client for the same MyCampusView backend the web
application uses. Not a WebView: every screen is native, talks to the public
`/api/v1` endpoints, and enforces the same tenant and permission rules.

```
mobile/
  app/                    screens (expo-router, file-based)
    (auth)/               sign-in, forced password change
    (app)/                the signed-in shell and its tabs
  src/
    api/                  client, typed hooks, response types
    auth/                 secure storage + session store
    components/           the shared UI kit
    navigation/           the module registry that drives navigation
    theme/                colour, spacing, type, radius, shadow
    config.ts             API origin and timeouts
  assets/                 icons and splash, generated from the brand master
  scripts/make-icons.py   regenerates those from public/brand
  android/                generated by `expo prebuild` — not committed
```

---

## Quick start

```bash
cd mobile
npm install --legacy-peer-deps
npx expo start                       # Expo Go / dev client
```

Point it at a server with `EXPO_PUBLIC_API_URL`. On an Android emulator
`localhost` means the emulator itself, so a local server is `10.0.2.2`:

```bash
EXPO_PUBLIC_API_URL=http://10.0.2.2:3000/api/v1 npx expo start
```

Unset, it defaults to `https://www.mycampusview.com/api/v1`.

## How it talks to the backend

Everything goes through [`src/api/client.ts`](src/api/client.ts). No screen
builds a request itself, because a screen that did could forget the tenant
header — and a request without one resolves no school.

Two headers carry the context the web gets for free from the browser:

| Header | Why the web does not need it |
|---|---|
| `Authorization: Bearer <token>` | The browser sends an httpOnly cookie. A native app has no cookie jar worth trusting and no shared subdomain to scope one to. |
| `X-Tenant-Slug: <school>` | The browser arrives on `school.mycampusview.com`, so the Host decides the tenant. The app is installed once and points at one origin. |

Both are additions to the backend, not replacements — see *Backend changes*.

## Authentication

Sessions were already opaque random tokens stored as SHA-256 hashes server-side
rather than JWTs, so the same credential works as a bearer token with no new
auth system. Revocation, expiry, "sign out everywhere" and the device list all
keep working for mobile exactly as for web.

1. **School** — `GET /site/school/:slug` resolves the code to a name and
   branding, so the password screen shows where you are signing in.
2. **Sign in** — `POST /auth/login` with `X-Session-Transport: bearer` returns
   `sessionToken` alongside the usual body. Without that header the response is
   byte-identical to what the web receives, so the browser never sees a token
   in a body it could read from script.
3. **Storage** — the token goes to `expo-secure-store`, backed by the Android
   keystore. Never `AsyncStorage`, which is an unencrypted SQLite file. The
   password is never stored in any form.
4. **Restore** — on launch the stored token is checked against `/auth/me`
   rather than trusted, so revoked sessions and changed roles are caught. If
   that call fails because the device is offline, the app opens on the stored
   session instead of stranding somebody at a sign-in screen they cannot
   complete.
5. **Expiry** — any 401 from anywhere clears the credential once and returns to
   sign-in with an explanation.

### Tenant isolation

The tenant header is **not** a security boundary, and nothing treats it as one.
Naming another school's slug resolves that tenant and then fails
`getContext`'s existing check that `user.tenantId === tenant.id`. Verified:

```
bearer token for "demo" + X-Tenant-Slug: springfield   →  401
```

## Permissions

`/auth/me` returns the same permission strings the web checks
(`students.view`, `fees.collect`, …; 145 of them across 39 namespaces). They
drive which tabs appear and which rows the More screen lists, from one registry
in [`src/navigation/modules.ts`](src/navigation/modules.ts).

This is presentation only. Every permission is enforced again server-side on
every call, so hiding a tab is a courtesy, not a control. The bottom bar is
chosen per user — a class teacher and an accountant do not need the same four
buttons.

## Backend changes

Additive and backward-compatible. The web application's behaviour is unchanged;
its login response, cookie and tenant resolution all work exactly as before.

| File | Change |
|---|---|
| `src/server/auth/session.ts` | `getSessionUser()` reads the cookie first, then `Authorization: Bearer`. `createSession` also returns the raw token. `destroyCurrentSession` revokes whichever transport was used. |
| `src/server/tenant.ts` | `resolveTenant()` falls back to `X-Tenant-Slug` when the Host resolves no school. Host is still tried first. |
| `src/server/auth/login.ts` | `LoginOutcome` carries `sessionToken`. |
| `src/app/api/v1/auth/login/route.ts` | Returns `sessionToken` **only** when the caller sends `X-Session-Transport: bearer`. |
| `src/app/api/v1/site/school/[slug]/route.ts` | **New.** Public school lookup for the sign-in screen. Rate limited; returns only what a login page already shows. |
| `src/app/api/v1/dashboard/route.ts` | **New.** Exposes the existing `getAdminDashboard` service, which the web renders in a server component. |
| `src/app/api/v1/admissions/*` | **New.** The admissions module had a full service layer and no HTTP surface at all. These call `listLeadsByStage`, `getLead`, `moveLeadStage`, `listFollowUps`, `createFollowUp` — no logic is duplicated. |

Nothing was rewritten to suit mobile, and no business rule moved out of the
backend.

### Two failures worth remembering

**`process.env.EXPO_PUBLIC_*` must be written out in full.** Expo's babel
plugin substitutes that exact member expression textually. A helper that read
`process.env[key]` was never rewritten, so the value was undefined on the
device and the app silently talked to production instead of the configured
server. It looks like a working abstraction and fails only after install.

**Gradle caches the JS bundle aggressively.** `createBundleReleaseJsAndAssets`
reported `UP-TO-DATE` after source changes that had been copied with preserved
timestamps, so three builds shipped stale JavaScript. Delete
`android/app/build/generated/assets/react` when a change does not appear.

## Building the APK

**This machine cannot build in place.** The repository lives at
`…\Lead AI Studio Project\School ERP\`, and ninja fails on paths containing
spaces with `manifest 'build.ninja' still dirty after 100 tries`. A directory
junction does not help — Gradle resolves through it to the real path. The
project must be **copied** somewhere without spaces.

```powershell
robocopy "C:\Users\aryan\Desktop\Lead AI Studio Project\School ERP\mobile" C:\mcvbuild `
  /MIR /XD "android\build" "android\.gradle" ".cxx" ".expo" /NFL /NDL /NJH /NP /MT:16
```

```bash
cd /c/mcvbuild/android
printf 'sdk.dir=C\\:/Users/aryan/AppData/Local/Android/Sdk\n' > local.properties
./gradlew.bat assembleRelease --no-daemon
```

`local.properties` must escape the drive colon or use forward slashes — a Java
properties file treats `\U` in `C:\Users` as an escape and silently produces a
path that does not exist.

Regenerate the native project after changing `app.json`:

```bash
npx expo prebuild --platform android --clean
```

That rewrites `android/`, so the signing block below has to be re-applied. It
is the one edit that does not survive a prebuild.

### Signing

`android/app/build.gradle` reads release credentials from
`android/keystore.properties`, or `-P` flags, or `ORG_GRADLE_PROJECT_*`
environment variables. With none present it falls back to the debug key so a
fresh clone still builds something installable.

```properties
# android/keystore.properties — gitignored, never committed
storeFile=app/mycampusview-release.keystore
storePassword=…
keyAlias=mycampusview
keyPassword=…
```

The keystore in this build is a **development key**, generated locally. It is
inside `android/`, which `.gitignore` excludes, so neither it nor the passwords
are in the repository.

> **Back the production keystore up before publishing.** Google Play ties an
> app to its signing key permanently. Lose it and you cannot ship an update to
> your own app — only a new listing under a new package name.

### App bundle for Play

```bash
./gradlew.bat bundleRelease
```

## Deliberate decisions

- **No offline write queue.** Reads survive a bad connection through the query
  cache and a banner says when data is stale. Queuing *writes* offline would
  mean an attendance register saved on a phone at 9am overwriting one taken on
  the web at 9:05, and the backend has no conflict rule to resolve that. Better
  to fail honestly than to lose a register.
- **Money in minor units.** The API speaks paise; the conversion happens once,
  in `src/lib/format.ts`. A screen that divided by 100 itself would eventually
  be a screen that forgot to.
- **No dark mode yet.** The web application has dark-mode tokens, so it is
  worth doing — but it is a presentation feature and functional parity came
  first.

## Not done

- **Push notifications.** `expo-notifications` is installed and configured, and
  the backend has a `POST /api/v1/push/subscribe` route, but nothing registers
  a token or sends one yet. It needs an FCM sender key on the server side, which
  is a credential this build does not have.
- **Uploads and downloads.** `expo-image-picker`, `expo-document-picker` and
  `expo-sharing` are installed and their Android permissions declared, but no
  screen uses them yet — the modules that upload (student documents,
  assessments) are the ones still web-only.
- **Deep links.** The `mycampusview://` scheme and intent filter are registered
  and expo-router maps URLs to routes, so links resolve; nothing generates them
  yet because that is the push notification payload.
- The web-only modules in the table above.
